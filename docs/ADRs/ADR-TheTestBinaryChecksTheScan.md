# ADR-TheTestBinaryChecksTheScan

- **Status:** Accepted
- **Date:** 2026-11-25

## Context

`--jobs-path` reads the test names off the source instead of asking the
compiler. A test the reading misses is not a job, so it never runs, and nothing
says so: the summary counts the jobs it was given, and the gate passes. That is
the failure `docs/ROADMAP.md` names as worse than having no gate -- a test
reported by omission as fine when it never ran.

A mutation-testing round found seven shapes `TestNameReader` returned nothing
for: a line, doc or block comment between the harness attribute and the
function, a comment trailing the attribute, the function on the attribute's own
line, `pub(crate) fn`, `unsafe fn`, and `#[ test ]`; `#[tokio::test(flavor =
"multi_thread")]` was not read as a harness at all. Each is fixed in the reader.
Fixing a shape fixes that shape, though; the next one somebody writes -- or a
test a macro generates, which no reading of the source can see -- is missed the
same way, silently.

## Decision

When the pre-build has found the test binary and the job list came from
`--jobs-path`, the binary is run once with libtest's `--list --format terse`,
and any test it lists that the scan did not find fails the run, named, before a
job starts.

## Forcing constraints / Evidence

The binary is the authority on which tests exist; the reader's own comment has
always said so. With discovery it is already built and its path is known, so
asking it costs one process start and no build. Asked with `--list --format
terse`, libtest prints one `<name>: test` line per test, a benchmark as
`<name>: benchmark`, and nothing else -- no summary line, as the pretty format
has. `cli/tests/system/test_list_runner_tests.rs` asks a real libtest binary,
the test binary itself, exactly as the core asks.

On this repository's own three test trees, the scan and the binaries' lists
name the same tests, one for one.

## Rejected alternatives

- **Take the job list from the binary instead of the source.** It would make
  `--jobs-path` a cargo-only feature -- today it works with any `--program` --
  and move the cargo concession from one optional path into the job list
  itself.
- **Parse the source with `syn`.** Still a reading: a test generated by a macro
  is invisible to any parse of the source, and the core depends on no crate.
- **Warn instead of failing.** A warning on a green run is read by nobody; a
  gate that passes has said everything it is going to say.
- **Hold `--jobs` and `--jobs-file` to the binary too.** A list stated by name
  is the caller's choice of what to run, a subset as often as not. Only a scan
  claims to be every test there is.

## Consequences

With discovery, a `--jobs-path` run fails when the binary holds a test the scan
cannot find, the error naming every such test on a line of its own. The remedy
is the caller's: write the test in a shape the reader knows, or state the list
with `--jobs-file`.

A scan that finds more than the binary lists is not refused: a name the binary
does not answer to runs no tests, and `JobWatch` fails that job, as it always
has.

Without discovery nothing checks the scan, and the reader's shapes are the
whole of the guard. A binary that cannot be started, or exits with a failure,
when asked to list its tests fails the run.

The core's libtest knowledge grows by the three listing arguments and the
`: test` suffix, on the same optional path as discovery. The process is the
`slotgate` crate's: `TestListRunner` implements the core's `TestLister` port.
`GateRunner::new` takes the lister third, and `PreBuildResolver` hands the
binary it found out separately, through `discover`, so the check can be told
it.

## Enforcement

`core/tests/config/scan_cross_check_tests.rs` asks for the terse list, refuses
a scan missing listed tests with every one named, and asks nothing without a
discovered binary or of a list stated by name.
`core/tests/execution/gate_runner_tests.rs` runs a whole gate whose scan misses
a listed test: it fails, says why on stderr and runs no job.
`cli/tests/invocation/entry_point_tests.rs` does the same end to end, against
the test binary itself, and asserts that no job started.
